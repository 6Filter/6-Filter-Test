## VERIFIED CAUSE OF THE ONE-SECOND "SCREEN AGAIN" PRESS (28 Nov, proved by changing one thing in a scratch copy). Do not re-investigate.
The output page presses `handleSubmit(..., { fromPending: true, forceResearch: true })`. With `confirmMissingSteps` true, `remainingEvaluateResearch(...)` (lib/evaluateRemaining.js) returns `force: true` and `onlySteps` = the steps still missing; the server then passes `onlySteps: repairMissing ? remainingOnlySteps : undefined` to `runPropositionResearch` (propositionsApi.js ~1590). Result: the press is treated as the pending page's "finish the missing steps", not as a new search. **Server log for the press: `research start ... force=true`, then `[primus/cost] calls=2 ... {"f5-sizing"}`: only the Filter 5 sizing ran (the only missing step), in about a second, and the sealed score stayed ("SCREENED IN 1S").** Changing only that token (not passing `confirmMissingSteps` for a forced press) makes the same press run Filter 1, price events and sizing.
**But that token alone is WRONG:** it makes an UNCHANGED idea re-run a $1+ search on every press, against the owner's rule (nothing changed: the stored result). The correct fix must satisfy BOTH tests in `testChangeIsNewSearch.mjs`:
